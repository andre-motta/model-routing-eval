# RHAISTRAT-1527: Multimodal Support in Gen AI Studio Playground

## Business Need (from RFE)

### **Problem Statement**

The current Gen AI Studio Playground supports text interactions only. As multimodal models become standard, users expect to work with images, audio, and mixed input types when exploring model behavior. Without multimodal capabilities, users cannot evaluate vision enabled or audio enabled models, test real world workflows, or build prototypes that rely on visual or auditory content.

This gap limits the usefulness of the Playground for early experimentation and prevents users from taking advantage of modern model capabilities. Users need a way to upload images, process visual content, handle audio input and output, and explore multimodal interactions within the same unified workspace.

### **Proposed Capability**

Add multimodal support to the Gen AI Studio Playground so users can interact with models that handle more than text. At minimum, this should include:

- Image upload and processing
- Display of model vision outputs
- Audio input support including microphone capture or audio file upload
- Audio output from models that support speech generation
- Ability to mix text, images, and audio in a single conversational flow

Users should be able to:

- Switch between text, image, and audio inputs
- Provide multiple images in sequence for iterative reasoning
- Play back audio responses directly in the Playground
- Combine multimodal inputs when comparing different models
- Store multimodal interactions inside persisted chats once chat persistence is available

### **Why This Matters**

- Enables realistic experimentation with models that support vision and audio
- Allows users to explore workflows such as document analysis, object recognition, image based prompt engineering, and spoken interaction
- Improves parity with modern commercial LLM interfaces
- Provides a foundation for agents that operate on visual data or use speech as part of a workflow
- Makes the Playground a complete testing environment for next generation AI applications

### **High Level Requirements**

- Support image upload including JPG, PNG, and PDF where available
- Support audio upload and microphone capture where permissions allow
- Render images and audio inside the chat interface
- Provide clear input type selection inside the Playground
- Ensure the request payload is compatible with supported multimodal models
- Add UI feedback for processing status and large file handling
- Provide guardrails if a model does not support a given modality

### **Dependencies and Considerations**

- Needs clear support boundaries for each model type
- Requires coordinated updates to model registry metadata to indicate capabilities
- Audio input may involve browser permission prompts that need thoughtful UX
- Future tie in with Configuration Persistence and Chat Persistence is expected
- Large file handling and cost implications need to be considered

### **MVP Scope**

- Image upload and vision inference using supported models
- Audio file upload and basic speech to text or audio to text functionality where supported
- Text combined with a single additional modality in one session
- Simple UI selector for input type
- Display of results in the existing chat transcript format

## Strategy (AI Generated by Agentic SDLC Pipeline)

### TL;DR

Add multimodal image and audio **input** support to the Gen AI Studio Playground by extending the GoLang Gen AI Studio BFF with server-side temporary file storage, base64 encoding, and a two-path inference pipeline: image content parts flow through OGX's Responses API to vLLM; audio goes through a user-registered ASR model (as an AI Asset in the AI Asset Endpoints table, bypassing OGX) and then the transcription text flows to OGX's Responses API. Per-modality input controls in the frontend are driven by model capability tags in the model-metadata-collection catalog.

**Components**: gen-ai-ui (frontend + BFF), OGX distribution (formerly Llama Stack), model-metadata-collection, kserve, vllm-cpu, vllm-gaudi

### Technical Approach

This strategy delivers multimodal **input** support to the Gen AI Studio Playground so that users can interact with models that accept images and audio alongside text, and receive text responses. Video input is not in scope (Staff Engineer direction). PDF upload is also not in scope — PDF handling belongs to the existing "Upload files" capability, which creates an inline vector store with embeddings. The implementation builds on the existing Module Federation architecture: the **gen-ai-ui** plugin (port 8143) handles both the Playground frontend and the **Gen AI Studio BFF** (`[packages/gen-ai/](https://github.com/opendatahub-io/odh-dashboard/tree/main/packages/gen-ai/)`), which is written in **GoLang** — not the main odh-dashboard Node.js/Fastify backend. All multimodal payload handling, file storage, base64 encoding, request body construction, and inference proxying must be implemented in the Gen AI Studio BFF. The main odh-dashboard backend proxies `/gen-ai/api/`* traffic to the gen-ai-ui container (port 8143). Authentication is provided via the forwarded access token (`x-forwarded-access-token` from kube-rbac-proxy).

**Critical architectural context — Responses API**: The Gen AI Studio Playground communicates with models using the OpenAI **Responses API** (`/v1/responses`), not `/v1/chat/completions`. This has two important implications that shape the multimodal approach:

1. **Image input**: The Responses API supports image content part inputs — **confirmed** by Staff Engineer. vllm-cpu v0.18.0 exposes `/v1/responses` (confirmed in architecture context); vllm-gaudi (v0.8.5.post1+Gaudi-1.21.3, built on vLLM v0.16.0) Responses API image support is likewise confirmed by Staff Engineer — the vllm-gaudi architecture docs list only `/v1/chat/completions`-family endpoints because the Gaudi plugin does not add or modify the upstream vLLM API server's endpoint set; the SE has verified image input works via the Responses API in the shipped RHOAI version. Image implementation can proceed without a pre-implementation SPIKE.
2. **Audio input**: The Responses API does **not** support `input_audio` content parts (Staff Engineer direction). Audio cannot be submitted natively to the Responses API. The audio approach therefore requires a **two-step ASR pipeline**: (a) the Gen AI Studio BFF receives the audio file from the frontend and makes a `/v1/audio/transcriptions` request to a user-selected ASR model deployed in the namespace, (b) the resulting transcription text is forwarded to the main model via the Responses API as a standard text message. This is a fundamental architectural difference from the prior assumption that audio would be submitted as `input_audio` content parts in `/v1/chat/completions`.

**Confirmed architectural context — OGX (formerly Llama Stack) routing layer**: Architecture context for the gen-ai BFF (`odh-dashboard.md`, API Routes table) confirms that the gen-ai BFF's `/api/v1/responses` route proxies to the **OGX API** (formerly Llama Stack, renamed per overlay 0003), not directly to a vLLM InferenceService. The upstream dependency for this route is listed as "LlamaStack API | HTTPS | auto-discovered | Bearer Token." The Staff Engineer has explicitly confirmed the routing for both modalities (SE Input, final clarification note):

- **Image requests**: The BFF passes the already-encoded base64 image content directly to **OGX's Responses API** (`/v1/responses`). OGX then proxies the request to the vLLM InferenceService. The full multimodal image inference path is: Browser → data-science-gateway (Envoy, port 443) → kube-rbac-proxy (port 8443) → odh-dashboard Fastify backend (port 8080) → gen-ai-ui GoLang BFF (port 8143) → **OGX API (port 8321)** → vLLM InferenceService.
- **Audio requests**: The BFF makes the `/v1/audio/transcriptions` call **directly** to the user-selected ASR InferenceService (outside of OGX — the ASR call bypasses OGX). The resulting transcription text is then forwarded to **OGX's Responses API** as a standard text message. OGX is in the inference path but not the ASR path.

This routing is **confirmed** (Staff Engineer). OGX is a firm dependency for multimodal inference, not conditional. The OGX Responses API image content part pass-through and body size limits must be validated before P0 image implementation begins.

**Scope**: This strategy covers multimodal **input** only — image and audio as input alongside text — producing **text output**. There is no native `input_audio` content part submission; audio goes through ASR transcription first. There is no multimodal output (no audio playback of model responses, no image generation). Streaming output is not in scope.

**Image support** is implemented via the Responses API. Responses API image content part support is confirmed for both vllm-cpu v0.18.0 and vllm-gaudi (built on vLLM v0.16.0) (Staff Engineer). The Playground frontend uploads the image file to the Gen AI Studio BFF, which stores it temporarily and returns a file ID. The BFF retrieves the stored file using the file ID, performs base64 encoding, and constructs the Responses API request with the image content included — there is no client-side base64 encoding (Staff Engineer direction). Supported image formats at MVP are JPG and PNG (confirmed minimum). Additional formats (e.g., WEBP) require a SPIKE to determine what works with supported models out of the box; a follow-up with PM is needed to set format priorities. vllm-gaudi ships HPU-optimized implementations for Gemma3, Qwen2.5-VL, and Qwen3-VL, providing a validated set of vision models for Gaudi hardware.

**Audio input** requires the ASR transcription pipeline (Staff Engineer direction). The Playground frontend accepts audio via file upload only (WAV, MP3 minimum) — microphone capture is explicitly not in scope per Staff Engineer direction. The frontend uploads the audio file to the Gen AI Studio BFF, which stores it temporarily and returns a file ID. The BFF then uses the file ID to retrieve the stored file, performs base64 encoding, and calls `/v1/audio/transcriptions` on the ASR model selected by the user from the Playground UI. The resulting text transcription is then forwarded to **OGX's Responses API** as a standard text message — there is no client-side base64 encoding (Staff Engineer direction; server-side storage is a hard requirement). Supported audio formats at MVP are WAV and MP3 (confirmed minimum). Additional formats (e.g., FLAC, OGG) require a SPIKE after the primary transcription method is confirmed. The ASR transcription call is made by the BFF **directly** to the user-selected ASR AI Asset endpoint (bypassing OGX); only the resulting transcription text flows through OGX via the Responses API. **BFF-to-ASR authentication is confirmed** (Staff Engineer): AI Asset endpoint models are OpenAI-compatible and already support Auth header + bearer token forwarding in Gen AI Studio; the bearer token type depends on the model deployment type and is an already-solved problem in Gen AI Studio.

**ASR model selection — AI Asset registration with audio model dropdown**: Users are responsible for deploying a transcription-capable model (e.g., Whisper or equivalent) and registering it in the Gen AI Studio **AI Asset Endpoints** table (Staff Engineer direction: "ASR models must be added as AI Assets to be visible in Playground, there needs to be additional UX added to the AI Asset Endpoints table to denote these models"). The Playground UI must expose an **audio model dropdown** that lists AI Assets registered in the AI Asset Endpoints table that have been marked as ASR-capable. The AI Asset Endpoints table is the single source of truth for what endpoints are available to the Playground — not the raw Kubernetes InferenceService list. New UX must be added to the AI Asset Endpoints table to allow users to flag an AI Asset as an ASR/transcription endpoint. The user selects the registered ASR AI Asset from the dropdown before submitting audio; the BFF routes the ASR transcription call to the endpoint URL stored in the selected AI Asset record. If no ASR AI Asset has been registered and flagged in the AI Asset Endpoints table, the audio input controls remain visible but the audio submission pathway is blocked with a clear user-facing message directing the user to register a transcription model as an AI Asset. Custom Endpoints (OpenAI/Anthropic) registered as AI Assets may serve as a fallback for end-to-end audio testing if no local ASR model is available. A SPIKE must validate the complete ASR transcription method and validate the end-to-end pipeline (audio → BFF file-upload → file ID → BFF retrieves and encodes → BFF calls the registered AI Asset ASR endpoint → transcription text → OGX Responses API). **BFF-to-ASR authentication is confirmed** (Staff Engineer): AI Asset endpoint models are OpenAI-compatible and support Auth header + bearer token forwarding; the bearer token type depends on the model deployment type (InferenceService, MaaS model, or custom endpoint) and is already a solved problem in Gen AI Studio. The ASR SPIKE focuses on validating the end-to-end pipeline mechanics (audio format handling, transcription quality, error propagation) and AI Asset Endpoints table UX, not on auth.

**Model availability and custom endpoints**: Which specific models in the RHOAI model registry support vision modalities requires investigation via a SPIKE. For audio, the ASR model (Whisper or equivalent) is user-deployed — users register it in the AI Asset Endpoints table and flag it as ASR-capable; the Playground audio dropdown draws from these registered AI Assets. As a fallback, Custom Endpoints (OpenAI/Anthropic) registered as AI Assets can be used to test and validate multimodal Playground behavior.

**File handling — server-side storage is a hard requirement**: Server-side temporary file storage in the Gen AI Studio BFF is **not** a stretch goal — it is the required architecture (Staff Engineer direction). There is no client-side base64 encoding. The file handling flow is: (1) the Playground frontend uploads the raw file (image or audio) to a new BFF endpoint; (2) the BFF stores the file temporarily in server-side storage and returns a file ID to the frontend; (3) when the user submits the prompt, the frontend passes the file ID to the BFF; (4) the BFF retrieves the stored file using the file ID, performs base64 encoding server-side, then constructs the Responses API request (for image) or calls the ASR endpoint (`/v1/audio/transcriptions`) followed by the Responses API (for audio). **Temporary storage design (required SPIKE, not stretch)**: The BFF temporary storage mechanism must be designed and validated in sprint 0. The Staff Engineer has indicated the expected mechanism is a **mounted volume** with the BFF responsible for file cleanup (SE Input: "most likely it will use a mounted volume that the gen-ai BFF will have to remove files from. It just requires the SPIKE to fully flesh out the implementation details and POC it."). This de-risks the design space — the mounted volume approach is the SE's working assumption. Key design questions for the SPIKE to validate and document: (a) volume type (emptyDir, shared PVC, ephemeral volume claim) — must be replica-safe for the 2-replica pod anti-affinity deployment (emptyDir is per-pod and not shared across replicas on different nodes; a shared PVC or another mechanism is needed unless sticky session routing is added); (b) eviction policy and TTL (files cleaned by the BFF after use or on TTL expiry); (c) per-user isolation (file IDs must be scoped to prevent cross-user file access); (d) cleanup on session end. Architecture context confirms the gen-ai-ui deployment runs 2 replicas with pod anti-affinity — in-memory artifact storage without sticky sessions or shared state is not viable. The SPIKE must complete before P0 image implementation begins. **File size baseline**: the gen-ai BFF already handles `/api/v1/files/upload` with a 10MB limit (confirmed in architecture context). This establishes that the proxy chain (Envoy, kube-rbac-proxy, Fastify, GoLang BFF) already supports 10MB payloads end-to-end. File size limit discussions should start from this 10MB baseline. File size limits must be enforced client-side (pre-upload validation) and at the BFF layer (configurable body size), and the agreed limit must not exceed the validated proxy chain capacity unless additional proxy chain configuration work is completed. The maximum file size agreed must also account for the BFF temporary storage capacity and eviction policy.

**Proxy chain body size**: The full traffic path for a multimodal image inference request is confirmed: Browser → data-science-gateway (Envoy, port 443) → kube-rbac-proxy (port 8443) → odh-dashboard Fastify backend (port 8080) → gen-ai-ui GoLang BFF (port 8143) → **OGX API (port 8321)** → vLLM InferenceService. Each hop may have its own request body size limit. The data-science-gateway Envoy and kube-rbac-proxy limits must be validated — the existing `/api/v1/files/upload` 10MB baseline confirms the chain already supports 10MB end-to-end (this path goes through the BFF but the `/api/v1/files/upload` route proxies to the OGX API per architecture context, making it a valid baseline for the BFF → OGX hop as well). For the agreed file size limit above 10MB, explicit validation is required for the OGX body size limit — OGX sits between the BFF and vLLM for image requests and its limit must accommodate the base64-encoded image payload (base64 adds ~33% overhead: a 10MB image becomes ~13.3MB in the Responses API request body). If Envoy or OGX body size limits cannot be raised via configuration, enforce a lower client-side limit that stays within the validated proxy chain capacity.

**Catalog extension fallback design**: The model-metadata-collection catalog is a **build-time artifact** shipped with each RHOAI release — adding `supported_modalities` requires a Go extractor code change and container rebuild; it cannot be patched at runtime. If the catalog extension misses the target release, a **fallback** is required: a manually curated static YAML file (format: `{model_id: [modality, ...]}`) committed to the gen-ai-ui repository, loaded by the BFF at startup as a config map or embedded file, consulted only when the catalog entry for a model lacks `supported_modalities`. This fallback location, format, and consumption mechanism must be designed and documented before the catalog extension work begins, so the team has a concrete recovery path if the release gate is missed.

**Model capability detection**: The model-metadata-collection component ships YAML catalogs (`models-catalog.yaml`, `validated-models-catalog.yaml`) volume-mounted into the dashboard pod at `/app/data`. These catalogs must be extended with a `supported_modalities` field (e.g., `["text", "image", "audio"]`) for each model entry. There is a verbal agreement that audio/image tags will be added to the model registry (Staff Engineer). The gen-ai-ui Playground reads the catalog to show or hide per-modality input controls — a separate control for each input type (image, audio), each shown or hidden based on model capability tags. There is no viable runtime fallback via `/v1/models` because vLLM's `/v1/models` endpoint returns model name and permissions only, not modality capabilities. The catalog extension is therefore the only reliable capability detection mechanism for the primary model. The ASR model used for audio transcription is separately user-managed — users register it in the AI Asset Endpoints table and flag it as ASR-capable; the Playground audio dropdown draws from these registered AI Assets, not from the namespace InferenceService list directly.

**Conversation history constraint**: Each conversation supports at most one image or one audio file in the entire conversation history — not multiple sequential images, not one image plus one audio in the same conversation. This is per Staff Engineer direction. The UI must enforce this limit and communicate it clearly to the user.

**Model registry tags**: The model-metadata-collection catalog extension must include specific tags as agreed with the model registry team: `image-inferencing` for vision-capable models and `audio-asr` (or equivalent agreed tag) for audio-input-capable models. The gen-ai-ui Playground uses these tags to determine which per-modality input controls to show. The Staff Engineer has confirmed that defining and registering these specific tags with the model registry team is a prerequisite before the catalog extension work begins.

**Modality-aware input controls**: Separate UI controls for each supported input type (image, audio). Each control is shown or hidden independently based on model capability tags from the catalog, not a single binary toggle. Text input is always available. If a model's tags are not yet in the catalog, the UI shows a clear error message at inference time if the model rejects a multimodal payload — guardrails are not implemented as hard submission blocks since this requires catalog metadata to be authoritative. Controls must be accessible (keyboard-navigable, screen-reader compatible per WCAG 2.1 AA) and provide clear user-facing feedback. When audio is enabled, the audio model dropdown (populated from AI Asset Endpoints marked as ASR-capable) is visible alongside the audio input control.

The architecture routes all Playground inference traffic through the Gen AI Studio BFF via `/gen-ai/api/`*. No new CRDs or Kubernetes resources are introduced by the feature itself; ASR model InferenceServices are user-deployed and user-managed.

### Non-Functional Requirements

- **Performance**: UI must display a processing indicator and not time out for at least 120 seconds for P0/P1 inference calls. Audio UI must communicate upload and ASR transcription steps separately (e.g., "Uploading...", "Transcribing audio..."). BFF must return a file ID within 3 seconds for files at or under the size limit under normal load (validate during QE). Proposed default file size limit: 10MB for both image and audio (matching existing `/api/v1/files/upload` baseline) — requires PM confirmation. File size limits and proxy chain body size limits must be agreed before implementation begins.
- **Security**: All payloads traverse kube-rbac-proxy; no new auth surfaces introduced for the primary model. BFF uses `x-forwarded-access-token` for inference calls; for ASR calls, BFF uses the existing Gen AI Studio bearer token forwarding pattern (auth confirmed by Staff Engineer — AI Asset endpoints are OpenAI-compatible; bearer token type depends on deployment type and is already solved in Gen AI Studio). No unauthenticated path to the registered ASR AI Asset endpoint. Audio dropdown scoped to the user's own AI Asset Endpoints context. MIME type allowlist enforced client-side and at the BFF. FIPS: confirm GoLang BFF file handling is `GOEXPERIMENT=strictfipsruntime` compatible; note vllm-gaudi removes `openssl-fips-provider-so` — FIPS-sensitive deployments should account for this.
- **Backwards Compatibility**: Text-only Playground behavior unchanged. No multimodal controls shown for text-only models. No existing API contracts, CRDs, or serving runtime manifests modified.
- **Scalability**: Each proxy hop (Envoy, kube-rbac-proxy, Fastify, GoLang BFF) must support the agreed maximum payload size. BFF temporary storage sized for maximum concurrent in-flight uploads; storage mechanism determined by required SPIKE.
- **Accessibility**: Per-modality controls and ASR audio model dropdown must be keyboard-navigable and screen-reader compatible per WCAG 2.1 AA. Inline image/audio rendering must include accessible labels and alt text. Automated axe-core scan of the modality control region must return zero WCAG 2.1 AA violations.

### Out-of-Scope

- **Video input**: Explicitly not in scope per Staff Engineer direction. If vLLM video API support matures in a future release, a follow-on strategy should be filed referencing this one.
- **PDF upload as image input**: Explicitly not in scope per Staff Engineer direction. PDF handling belongs to the existing "Upload files" capability in the Playground, which creates an inline vector store with embeddings derived from the file. Users wishing to use PDF content with vision models should extract images separately before uploading.
- **Native `input_audio` content part submission**: The Playground uses the Responses API which does not support `input_audio` content parts. Audio is handled via the ASR transcription pipeline (user-deployed Whisper or equivalent → text → Responses API), not native audio content parts in an inference request. The confirmed `input_audio` support in vllm-cpu v0.16.0 and vllm-gaudi v0.14.1 (for `/v1/chat/completions`) is not used by this strategy given the Responses API constraint.
- **Multimodal output**: This strategy covers multimodal **input** only. There is no audio output playback from models, no image generation, and no video output. All model responses are text. Note: the RFE explicitly requested audio output/playback — this scope is excluded per Staff Engineer direction because the technical implementation is completely different from image and audio input. A follow-on STRAT or RFE update must be created by PM to track this gap; it is not abandoned, only deferred to a separate strategy.
- **Audio streaming / real-time voice conversation**: The WebSocket-based `/v1/realtime` API for continuous voice interaction is deferred. This strategy covers file-based audio upload only with a single-shot ASR → text → Responses API flow.
- **Browser microphone capture**: Microphone capture (MediaRecorder API) is explicitly not in scope per Staff Engineer direction. Audio input is file-upload only (WAV, MP3 minimum). A follow-on strategy or enhancement can add microphone capture if there is PM demand.
- **Multiple sequential image inputs in a conversation**: This strategy supports at most one image or one audio file per conversation history. Multiple sequential images for iterative visual reasoning are not in scope per Staff Engineer direction.
- **Streaming output from multimodal inference**: Partial/streaming text output while the model processes an image is not in scope. All responses are returned as complete text messages.
- **Image generation / diffusion models**: This strategy covers image input (vision), not image output (generation). Text-to-image models require a separate strategy.
- **Persistent server-side file storage**: Long-term file management (user libraries, cross-session artifact reuse) is out of scope. The required BFF temporary storage handles files only for the duration of a single inference request, with TTL-based eviction. No cross-session or cross-user artifact persistence is in scope.
- **Multimodal guardrails integration**: Content safety scanning of uploaded images or audio via fms-guardrails-orchestrator is a separate concern and not gated by this strategy.
- **Cross-model multimodal pipelines**: Chaining a vision model output to another model is an agentic workflow pattern, not a Playground feature.
- **Custom model capability registration UI**: Admins cannot manually tag models with modality support through the UI. Modality metadata comes from the model catalog only.
- **Main Dashboard BFF changes beyond proxy body size**: The core odh-dashboard backend requires no multimodal-specific logic. All inference proxying is scoped to the Gen AI Studio BFF.
- **ASR model lifecycle management**: Provisioning, deploying, updating, and managing the lifecycle of the ASR model (Whisper or equivalent) InferenceService is out of scope for this strategy. Users are responsible for deploying their own transcription-capable model and registering it as an AI Asset in the AI Asset Endpoints table; the Playground audio dropdown draws from registered AI Assets.
- **Cross-tenant ASR AI Asset selection**: The audio model dropdown lists only AI Assets registered in the user's own AI Asset Endpoints context. Selecting ASR models from other users' or tenants' AI Assets is not in scope.

### Acceptance Criteria (Proposed — requires PM/Engineering validation)

- Vision-enabled model selected + JPG/PNG uploaded within size limit → image displayed in chat, non-empty text response returned within 120s. Parameterize for both JPG and PNG.
- Text-only model selected → no image or audio input controls visible in the DOM.
- Vision-only model selected → image control visible, audio control hidden. Per-modality visibility matches `supported_modalities` catalog entry.
- Audio-capable model selected, no ASR-capable AI Asset registered in AI Asset Endpoints table → audio control visible but submission blocked with user-facing message to register a transcription model as an AI Asset.
- Audio-capable model selected, ASR AI Asset chosen from dropdown, WAV file uploaded → BFF calls the registered ASR AI Asset endpoint at `/v1/audio/transcriptions`, receives transcription, forwards text to OGX Responses API, non-empty response returned within 120s. Parameterize for WAV and MP3.
- ASR-capable AI Asset registered in the AI Asset Endpoints table → audio model dropdown lists that AI Asset as a selectable ASR endpoint.
- File exceeds size limit → client shows error, no upload request sent to BFF.
- File MIME type not on allowlist → client rejects with validation error before upload.
- Model switched → modality controls update within 500ms without page reload.
- ASR InferenceService unreachable or returns error → user-facing transcription failure message shown, no Responses API call made.
- Silent audio file produces empty ASR transcription → user-facing message shown, no Responses API call made.
- Zero-byte file selected → client shows validation error, no upload request sent.
- `validated-models-catalog.yaml` has non-empty `supported_modalities` for every vision/audio model after schema extension ships.
- Second image or audio upload attempted in same conversation → upload blocked with one-file-per-conversation-history message.
- After multimodal session, text-only interaction succeeds with no state leakage from prior session.
- File uploaded to BFF, file ID returned, prompt submitted → BFF retrieves and encodes file correctly regardless of which replica handled the upload (validate with cross-replica integration test).
- Modality control region (including ASR dropdown) returns zero WCAG 2.1 AA violations in axe-core automated scan.

### Effort Estimate

**L (5-7 sprints)**

Justification: Microphone capture removal and the one-image-or-audio-per-conversation-history constraint (Staff Engineer direction) reduce frontend scope. However, BFF server-side temporary file storage is now a **hard requirement** (not a stretch SPIKE), adding a required sprint-0 design-and-implement task. The revised scope is: (a) BFF server-side temporary storage design and implementation (required SPIKE — expected: mounted volume) — 1 sprint in sprint 0, blocking both image and audio; (b) image file upload P0 — 1-2 sprints post-storage SPIKE; (c) audio file upload P1 via ASR pipeline — 1-2 sprints post-ASR SPIKE; (d) model catalog extension and cross-team coordination — 1-2 sprints; (e) sprint-0 validation items: OGX content-part pass-through validation (routing confirmed, behavior must be tested), BFF-to-ASR auth validation, proxy chain body size, model registry tag name agreement. The lower end (5 sprints) applies if the storage SPIKE, ASR SPIKE, BFF auth validation, OGX content-part pass-through validation, and proxy chain checks all complete cleanly in sprint 0/1 and the catalog extension ships with the target release. The upper end (7 sprints) applies if the storage SPIKE reveals that a shared RWX PVC is unavailable (requiring a sidecar cache) and takes more than one sprint, BFF auth validation reveals a new auth design requirement, OGX requires code changes to pass image content parts, the AI Asset Endpoints table UX extension for the ASR capability flag requires more design/backend work than anticipated, or the proxy chain requires operator-level changes outside the AI Studio UI team's control. The lower bound remains 5 because server-side storage adds a non-negotiable sprint-0 SPIKE; the upper bound rationale for "OGX being in the path and requiring additional validation" is now partially resolved — routing is confirmed, but OGX code changes (if content-part pass-through fails) remain an upper-bound driver.

## Staff Engineer Input

The BFF that we should use for this is not Dashboard BFF but instead Gen AI Studio BFF [https://github.com/opendatahub-io/odh-dashboard/tree/main/packages/gen-ai/](https://github.com/opendatahub-io/odh-dashboard/tree/main/packages/gen-ai/)

Question: Should the Playground support streaming vision responses (partial text output while the model processes an image)?. Answer: Streaming vision/audio output is not in scope for this STRAT.

Question: Does the Gen AI Studio BFF Fastify body limit need an operator-level configuration knob, or is a code-level default sufficient? Answer: The BFF is written in GoLang, so fastify is not applicable here.

Question: What is the interaction model between this feature and the Chat Persistence RFE when both are available? Answer: The chat persistence RFE will handle persiting multi-modal content in the chat messages.

Question: How should the Playground handle models that support vision but not audio, or vice versa? Answer: There should be a separate control for each input type (I.e. audio, image), with each being available depending on the model tags

Note: There is a verbal agreement that audio/image tags will be added to model registry

Question: How does this feature interact with the Chat Persistence RFE's multimodal message serialization format? Answer: This STRAT does not need to be concerned with this, chat persistance's RFE will handle this.

Note: Video input is not in scope for this feature. 

Note: It is confirmed that input_audio and image_url is supported in those versions of vLLM cpu and vllm Gaudi

Question: Which specific vision and audio-input models will be validated for RHOAI 3.5? Answer: Need to include a SPIKE to investigate which current models in the model registry support this. At worst, it can be used with the custom endpoints feature, that let's you connect with models from OpenAI and Anthropic.

Question: What audio file formats beyond WAV and MP3 should be supported at MVP (e.g., FLAC, OGG, M4A)? Answer: Minimum requirement is WAV and MP3, there needs to be a SPIKE to investigate what other will work out of the box and a follow up to PM for what the priorities are.

Question: What image file formats beyond JPG, PNG should be supported at MVP (e.g., WEBP, GIF)? Answer: Minimum requirement is JPG and PNG, there needs to be a SPIKE to investigate what other will work out of the box and a follow up to PM for what the priorities are.

Note: Uploading PDF files as images is out of scope, that will need to be done from the existing "Upload files" capabilities, which creates an inline vector store with embeddings created from that file.

Question: Should audio output/playback (excluded from this strategy per Staff Engineer direction) be tracked as a follow-on RFE or a new STRAT? Answer: Yes, because the technical implementation is completely different than image + audio in.

Note: Responses API, which is used for communicating with a model in Playground, does not have audio input support, unlike /v1/chat/completions. For this STRAT, there needs to be a SPIKE to validate the transcription method for audio. The idea is that a separate audio transcription model needs to be available in the namespace (e.g. openAI's whisper), and the BFF will make a /v1/audio/transcription request against the model, then forward that text to Llama stack's Responses API

Note: For image input, it is confirmed that Responses API has support for this

Question: Which ASR model (Whisper or equivalent) will be used for the audio transcription pipeline, and how will it be made available in the RHOAI namespace? Answer: A user will have to deploy a transcription capable model in the namespace and there should be an audio model dropdown that is selectable from the UI.

Note: Multiple sequential image inputs within a single conversation for iterative visual reasoning is not in scope. Only one image or audio per conversation history.

Note: [P1] Browser microphone capture via MediaRecorder API with guided permission prompt UX and graceful fallback when permission is denied. This is not in scope, no microphone capturing, can only upload audio files.

Note: [P2] Mixed text + image + audio in a single message (full multi-modality mixing within one turn). Change: Only one audio or image file in a single conversation history.

Note: [P0] Guardrails preventing submission of image or audio content to models that do not support the modality, with clear user-facing error messages. Change: Guardrails are not in scope. The ideal UX is to have model tags to guide a user to select a supported model. If these tags are not supported, we need clear user-facing error messages when attempting to inference.

Note: The STRAT needs to include the specific tags that are required from the model registry team: Audio/ASR and image input.

Note: The new plan is for the client side to not handle the B64 encoding, instead it will pass some form of file ID to the BFF, and the BFF will be responsible for fetching it, doing the B64 encoding, calling the /v1/audio/transcriptions endpoint.

Question: What mechanism will be used to identify ASR-capable InferenceServices in the namespace for the audio model dropdown? Answer: This is coming from the tags we require from the model registry team (Audio/ASR and image input)

Note: There is no client side B64 decoding, it will be done on the server side now that storage is a hard requirement.

Note: There is minimal risk with the file storage solution, most likely it will use a mounted volume that the gen-ai BFF will have to remove files from. It just requires the SPIKE to fully flesh out the implementation details and POC it.

Note: When using OGX's responses API with images, the BFF will pass in the already encoded B64 contents.

Clarification: For this unknown The strategy must resolve **which path multimodal Responses API requests actually take through the BFF** before implementation begins. When using images, it will pass the B64 content directly to OGX's repsonses API. When there's audio input, it will separately call the /v1/audio/transcription endpoint outside of OGX and then pass the transcription as part of the input to OGX's responses API.

Note: ASR models must be added as AI Assets to be visible in Playground, there needs to be additional UX added to the AI Asset Endpoints table to denote these models.

Note: In the event we don't have the audio and image model tags, the workaround is to have error handling around what happens when a user calls a model with an unsupported function. No hardcoded list.

Note: The STRAT exceeds the 32K character limit for a JIRA description.

Note: AI Assets endpoint models just abstract different types of model deployments: InferenceServices, MaaS models, custom endpoints. Under the hood they are still model deployments.

If not, what authentication pattern is viable, and what are the namespace scoping implications for the fallback? Answer: The AI Assets endpoint models will be OpenAI compatible and can have an Auth header + bearer token forwarded.
